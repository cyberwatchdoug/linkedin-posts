Master these Kubernetes differences when working with k3s, or your monitoring may break in unexpected ways.

k3s isn't "just lightweight Kubernetes" it's architecturally different in ways that challenge standard monitoring setups.

Here's what you need to know before deploying monitoring to your k3s clusters:

🎯 Architecture Difference #1: Single Binary vs Multi-Process
Traditional K8s: Separate processes for each control plane component
k3s: All control plane components in ONE binary (API server, scheduler, controller-manager, kubelet, kube-proxy)

🎯 Architecture Difference #2: Data Storage
Traditional K8s: Requires etcd cluster
k3s: Uses SQLite by default, no etcd endpoint for metrics scraping

🎯 Architecture Difference #3: Metrics Exposure
Traditional K8s: Components expose metrics automatically  
k3s: Metrics bound to localhost unless manually configured (with bind-address)

🎯 Architecture Difference #4: Container Runtime
Traditional K8s: Docker/containerd as separate services
k3s: Embedded containerd (up to 70% less resource usage)

🎯 Architecture Difference #5: Networking
Traditional K8s: Complex CNI setup required
k3s: Flannel + Traefik built-in, simplified networking model

🚨 Monitoring Impact
Standard Prometheus configs fail because they expect:
❌ Separate control plane pods that don't exist
❌ etcd metrics that aren't available  
❌ Network-accessible metrics endpoints
❌ Multi-node service discovery patterns

✅ k3s Monitoring Fix

Update [/etc/rancher/k3s/config.yaml] with bind-address configs for:
• kube-controller-manager
• kube-scheduler
• kube-proxy

Adjust Helm values:
• Disable kubeEtcd monitoring
• Skip duplicate API server scraping
• Configure manual endpoints for control plane components

Understanding architecture → Successful monitoring.

Ignoring architecture → Hours of debugging.
